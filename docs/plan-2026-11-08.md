## 13. The agency instruments — the honest version (5 Nov 2026)

### Context
On 31 Oct the questing lane was refused on the numbers, and the "cheapest decisive test" for the brand side was named
as *does one limited drop to the existing list beat a plain email to the same list?* A draft analyser,
`agency/scripts/ab-test.mjs`, was written before plan mode was reasserted: **uncommitted, untested**. A read-only
ultracode sweep then ran (44 agents: 3 lenses on the draft with every finding refuted twice, 3 researchers, a designer,
a synthesiser). **15 of 18 findings survived** two refutations; 3 were refuted.

### The finding that changes the plan
**The test I recommended cannot settle anything at Leif's scale.** Klaviyo's 2026 benchmark (SUMMARY, not opened)
puts a clothing *campaign* email at **~0.12% placed orders per recipient** (range 0.07–0.13%; flows run 15–20× higher
and must never be blended in). The draft assumed 3–5%. Verified independently with the corrected formula (it matches
the reviewers' table exactly: 0.05/50% → 1,471; 0.03/100% → 749):

| Recipients needed **per arm** (α .05, power .80) | +20% | +50% | +100% |
|---|---|---|---|
| Placed orders, 0.12% (Klaviyo clothing) | 359,265 | 65,309 | **19,586** |
| Clicks, 1.70% (fashion, UNVERIFIED) | 24,918 | 4,518 | 1,349 |

So detecting even a **doubling of orders needs ~39,000 on the list.** And the draft made this *worse* by hiding it: its
formula understated the sample by up to a third (the dangerous direction), and its own example baseline was 30× too
high. The instrument's most valuable output is therefore **"don't run this — the cheaper arm stands"**, given *before*
a send is wasted. That is the plan, not a consolation.

### Build 1 — fix `agency/scripts/ab-test.mjs` (the 15 confirmed defects, merged)
1. **Sample size** — replace `requiredPerArm` with the standard two-proportion formula
   `p2=p(1+L); p̄=(p+p2)/2; n=⌈(z_a√(2p̄(1−p̄)) + z_b√(p(1−p)+p2(1−p2)))² / (p2−p)²⌉`, `null` if `p2≥1`.
   `detectableLiftPct` becomes a bisection on that function (no closed form exists). Add a hard floor: fewer than 10
   expected conversions in the smaller arm is `INSUFFICIENT_SAMPLE` whatever the bar says. Delete the "accept a larger
   minimum lift" advice — raising the bar to get past the gate is gaming it. Tests pin 1,471 / 749 / 19,586.
2. **Revenue ties** — compare revenue per recipient by exact integer cross-multiplication in cents; a tie is "level"
   (no false divergence, which the draft raised on every all-$0 case). `conversions > 0` with `revenueUsd === 0` is
   `INVALID_DATA` (revenue was not recorded).
3. **Identity, not names** — `divergent = moneyWinner !== winner` by object; arm names required, trimmed, distinct.
4. **Divergence never returns WINNER** — if the conversion winner earns less per recipient, the verdict is
   `NO_CLEAR_WIN`. No revenue permutation test is built: at this scale the pre-flight stops the test long before it
   would run (revisit only if a list ever clears the gate).
5. **The metric is honest** — `preRegistered.metric` must be `conversion_rate`, the one thing the code tests; the label
   is fixed, not echoed from input.
6. **Strict dates** — only `YYYY-MM-DD` or a full timestamp with `Z`/`±hh:mm`; round-trip checked (rejects 2026-02-30),
   no slash dates, no bare numbers. The draft read Australian `3/12/2026` as 12 March and let a rule fixed **after**
   the send through. Date-only values compare by calendar day and the rule must be **strictly earlier**; no future dates.
7. **Strict parsing** — counts must be whole numbers written as digits; no `""`, whitespace, arrays, hex or exponents
   (the draft turned blank-looking cells into valid zeros).
8. **No peeking** — pre-register `plannedPerArm` (≥ the required n, else "underpowered by design"),
   `conversionWindowDays` and `analyseOn`; the experiment carries `analysedOn`. Earlier than planned, or an arm >5% short,
   is `TOO_EARLY` with **no p-value printed at all**. One look only.
9. **Inconclusive is named for what it is** — `NO_DIFFERENCE` becomes `INCONCLUSIVE_DEFAULT`, returning the
   pre-registered `defaultArm`, the 95% CI of the difference, the detectable lift at the real arm sizes, and the line
   "this list could not tell them apart; it does not show they are equal".
10. **Alpha/power** normalised before lookup (the draft refused `"0.10"` with a self-contradicting message).
11. **Display only, per the refuters** — the lift is printed as the winner over the loser, and the bar is labelled
    "planned minimum lift (it sized the test)". **No** below-bar verdict: two skeptics simulated it cutting real power
    from ~63% to ~44% at exactly the registered effect, and the minimum lift sizes a test rather than thresholding it.
12. **`--check`** validates the pre-registration with no data, so the tool refuses *before* the send. **`--preflight`**
    takes `--metric orders|clicks` with the researched baselines built in, and prints required n, detectable lift at
    half the list, and expected conversions per arm.

Verdict order: `NOT_PRE_REGISTERED → INVALID_DATA → TOO_EARLY → INSUFFICIENT_SAMPLE → INCONCLUSIVE_DEFAULT →
NO_CLEAR_WIN → WINNER`; exit 0 only for `WINNER`. Kept unchanged on the evidence: the two-proportion z-test (two
refuters showed the sample gate already guarantees adequate expected counts wherever a verdict can be reached).

### Build 2 — `agency/scripts/creator-pilot.mjs` (the instrument that works at any scale)
This is accounting, not statistics, so list size does not limit it — which makes it the primary revenue instrument
now. Per the 27-guard design: an append-only JSONL ledger; **money held as whole cents** so float drift cannot move
the $600 cap; a result is **verified** only if tied to a unique code and a real store order id (duplicates, wrong
source, unknown code, self-use, refunds, out-of-window all refused with a named reason, and unverifiable is unpaid);
the cap checked **before** any payout is written; refunds netted and clawed back; day-30 stop at >30% of the
**pre-pilot** AOV (so a creator cannot inflate their own denominator) or zero orders; day-60 continue only below $30
blended per verified order; reach fields (likes, follows, views) refused outright. Buyer and account identifiers stored
only as sha256 hashes, never raw emails.

Defaults chosen (change in `pilot.json`; none blocks the build): day 30 counts from programme start; "beats the band"
means below its $30 end; an order and a sign-up from the same person both pay; a creator stopped for cost is still paid
what they earned before the stop; earnings under an open fraud flag are held.

### Build 3 — the template and the run-sheet
- `agency/experiments/drop-vs-email.json`: pre-registration filled in with `baselineRate 0.001`, its source labelled
  SUMMARY with the 0.07–0.13% range, `defaultArm: "plain email"`, and the instruction to replace the baseline with
  Joyisfree's own **campaign** rate (never flows) before `decidedOn`.
- `agency/RUN-drop-vs-email.md`, one page: run `--preflight` first and expect TOO SMALL; if so, **send the plain
  email and stop** — the research-backed rule for low stakes is to pick the cheaper option. If the list is ≥ ~2,700,

  within **5 working days** (ACMA; one blog's "10" is wrong). **Attach no prize draw to the drop**: SA, ACT and NSW

  marketing one. Hold send time, subject, offer, price, imagery and sender equal; split randomly within one list.
- `agency/README.md` and `agency/docs/state.md` (each track has its own, per the repo's CLAUDE.md).

### Only Leif's
